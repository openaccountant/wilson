## Headline

- **Arm O was not run on v4, and the harness would not run it.** The frozen file `specs/eval/round4-openjev-frozen.json` (sha256 `8994d51d9c0837ec57460f4ac291c0bfb067004fee5251e509643d32d35758ac`) has `cut: null`: the pre-registered dev procedure found no viable cut (`2026-10-03-round4-dev-cut.md`), so arm O is disabled by spec §5 step 6. The harness hash guard was exercised: without `--frozen-sha` it refuses (`pass --frozen-sha ...`); with the correct sha256 it refuses on the null cut (`the frozen cut is null (arm O disabled; skip this run)`, exit 8). Running arm O anyway would have meant editing the frozen file or the product constant, which burns v4. I did neither. **Arm O therefore cannot meet "coverage >= T + 5 pp" (no O rows exist; delta undefined, recorded as not met). Verdict for O: NO-GO by construction.**
- **Arm T (templates, keyword-only routing) ran on all 193 rows on real WebGPU, twice, with 0 differences** in gate, hits, route, via, outcome, reason or answer text across the 193 rows.
- **T answers 9 of 139 read rows locally: coverage 6.5%** (informational target 35%, not a gate). Every answered row used the expected tool. 9 answers means the 97% precision bar allows zero wrong-or-useless answers (one wrong = 88.9%). **Bars 2 and 3 are pending the blind grading** of `specs/eval/2026-10-03-round4-blind.jsonl` (9 lines).
- Bar 1 and bar 5 pass for T. The open-jev model loads and decides fine in the browser (cold 17 to 21 s, warm worker 1.0 s, ~65 ms per decision) and co-resides with Qwen3-0.6B with no device or page errors, but with a null cut none of that gets used on the turn path.

## How it was run

- Playwright full Chromium 153.0.8010.12, headless; adapter vendor `apple`, architecture `metal-3`, `isFallbackAdapter: false`, `shader-f16: true`. The product's `createModelEngine` in a module Web Worker (transformers.js 4.3.0, ORT-web 1.31-dev) and the product's unmodified `runSubagent` loop (gate, keyword router, `fillArgs`, one tool step, template compose, `classifyLocalOutput`). Tools run on the real mirror executors in a bun sidecar, one mirror per persona (synthetic personas from `<main checkout>/scripts/demos/personas`, read-only; no `~/.openaccountant` data).
- Arm T: `--arm T --compose template`, Qwen3-0.6B q4f16 loaded but idle (zero compose generations), fresh profile per run. First-load / warm-respawn Qwen load: 28.7 s / 1.5 s (run 1), 25.1 s / 1.6 s (run 2).
- Arm O load and latency: `--arm O --sets bench` (the harness's fixed bench questions, **not** v4; the held-out guard only applies to `--sets heldout`). Co-residence: `--arm O --sets bench --limit 4 --coresident` (new flag, below).
- Mutation flag: from the v4 row's own `mutation` field; the denylist flag (row contains a `MUTATION_VERB` word) is computed from the product source: 23 of the 28 mutation rows are verb-less in the product's sense (the v4 writer's own summary says none contain a verb, "even as a substring", so the other 5 contain a verb from the product's current `MUTATION_VERB` ("get rid of", "put", "overwrite", "reclassify", "reassign"), so the list the v4 writer was given evidently lacked them. All 5 were held by the `mutation-intent` gate. Reported as measured; they do not count toward the 15 verb-less rows).

## Co-residence: Qwen3-0.6B q4f16 and open-jev in one tab (spec C14)

Both models loaded in the same Chromium tab on the same adapter (Qwen first, then open-jev). Workload: 8 solo Qwen turns, 12 solo open-jev decisions, then 8 blocks each running 3 Qwen turns concurrently with 8 open-jev decisions, then one of each afterwards. A Qwen turn is the model-compose subagent path (`--compose model`), which shares `engine.generate` with bundle mode; bench questions only.

- **Errors: 0. Device-lost signals: 0. Page console/page errors during the block: 0.** Both models still answered after the concurrent phase (Qwen 296 ms, open-jev 66 ms).
- Open-jev decide: solo p50 67 ms, p95 69 ms; **concurrent with Qwen p50 84 ms, p95 157 ms, max 162 ms** (n = 64). Slower, still under the 400 ms chat timeout.
- Qwen generations (only the net-worth question reaches a compose generation; the other bench questions hand off before one): solo median 312 ms (n = 4), concurrent median 355 ms (n = 12), max 367 ms.
- Limits: the Qwen generations are short (about 300 ms), so the overlap is real but brief; this is not a long-decode stress test, GPU memory was not read out (no browser API for it), and bundle mode itself (the dashboard's Qwen path) was not driven through the UI. "No device error under this workload" is the claim, no more.
- Load times in the co-resident run (fresh Qwen cache in that profile): Qwen first load 31.0 s, warm respawn 1.5 s; open-jev load 18.3 s, warm 0.9 s.

## The blinded grading file

`specs/eval/2026-10-03-round4-blind.jsonl`: one line per locally answered row, shuffled, opaque 10-hex ids. Fields: `id`, `q`, `expect`, `answerNotes` (the v4 writer's), `tool`, `args`, `toolResult` (full), `answer`. No arm label. Because arm O has no rows, all 9 lines come from arm T and the file carries no decoys. The grader needs only this file. The id-to-arm key is **not in the repo**: it was written to `${SCRATCH}/round4-key.json` and stays closed (with one arm it only maps ids to row indices and personas, which `answerNotes` resolution may need; open it after grading or give the grader persona-resolved notes if needed). `2026-10-03-round4-results.json` holds per-row results **without answer text** (no `text`/`answer` field; checked: no answer line from the blind file appears in it).
Suggested rubric: unchanged (Round 2/3): tool correct AND every figure and claim matches the tool result and notes AND not useless (period and label stated, what-if applied, empty period called out). Row-specific flags for the grader, not pre-graded: "is my car worth more than the loan" was answered with the plain net-worth summary (a comparison the template may not express); "did we come out ahead in june" is an interpretive profit_loss question.
